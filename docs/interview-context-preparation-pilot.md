# Context-aware preparation: developer pilot

Date: 2026-10-25. These are two inspected fictional development contexts, not a holdout or calibrated quality benchmark. Planning methods: `simple-instruction-v1` and `context-balanced-v1`; configured agent: `gpt-6-luna`, high effort, CLI 0.163.0.

## Inputs and comparison boundary

C03 is a 20-minute graduate-backend recruiter/HR preparation case; C08 is a 50-minute junior-modeling-DS case whose current interview explicitly focuses on experiment design and product metrics. A new real context-analysis call for C03 completed and passed its mechanical contract; C08 reuses the retained guided context from the previous context-node pilot.

Within each planning pilot both methods receive identical public planning payloads for a given case: the same captured sources, supplied analysis, budget and common contract. Fresh business state prevents one method seeing the other's proposal. This isolates a planning-instruction contrast under supplied context, not an end-to-end simple baseline versus a complete workflow. No retrieval or memory effect is measured.

The predeclared audit accepts only C03/context-balanced using `synthetic_test_script` provenance and then generates matching materials. This is a fictional mechanics check, not actual user acceptance or an independent judgment of plan quality. Other proposals remain unapproved. No live Google/calendar/email operations occur.

## Retained first pilot

The private initial run is named `context-preparation-pilot-20261025`, node protocol v1. Four proposals and one materials audit were attempted; all five model invocations completed. C03 simple/guided and C08 guided passed mechanical proposal validation. C08 simple failed because a section lacked an included coverage link. The C03 guided materials audit passed.

Developer inspection found that the mechanically valid C08 guided proposal deferred introduction, why company, why role, behavioral and interviewer-question preparation. The technical focus was correct, but omitting all common motivation/introduction preparation did not meet the user's stated preference. This is a concrete example of a semantic problem that a valid JSON/time/coverage ledger did not catch.

The correction adds a configurable common policy requiring brief introduction/why-company/why-role work by default. The same policy is supplied and enforced for both methods. It can combine areas in one compact block and can change for explicit user instructions. This is a revised task constraint, not a measured contribution of guided instructions. The old run, outputs and finding remain unchanged.

## Separate policy-v1.1 pilot

The private revised run is `context-preparation-core-v1.1-pilot-20261025`, node protocol v1.1. All four proposals passed the shared mechanical checks; the one predeclared C03 materials audit also passed. All five invocations completed in distinct sessions with zero command calls. Source and implementation audits confirm identical payloads across planning methods and identical implementation snapshots within this run. The two protocol versions are not pooled.

Guided C03 allocates 6 minutes to introduction/why role, 3 to why company, 7 to a collaboration story and 4 to availability/interviewer questions. Its materials match those blocks with concrete prompts, steps, answer structure and self-checks. Unknown personal motivation, availability, project impact and production ownership remain prompts or explicit limits.

Guided C08 allocates 12 minutes to introduction/motivation, 26 to experiment design/product metrics, 8 to a bounded project/behavioral story and 4 to interviewer questions. It keeps modeling implementation out of this round, uses applied early-career depth, and does not invent healthcare deployment, project impact, collaboration details or personal motivation. This is qualitative assistant/developer inspection, not an independent human score.

Passing the shared policy does not prove that a block is realistic, a story is useful, or the method is better. Every semantic-quality field remains `pending_unrated`. A formal evaluation needs stage-specific anchors, broader reviewed stories, independent ratings and matched methods under a frozen protocol. These inspected outputs must remain development data.
