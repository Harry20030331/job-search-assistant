# Complete interview simulations

Maintenance date: 2026-10-26. The user requested realistic DS/SWE practice rather than one-line prompts. The opt-in `simulation-v2` contract adds self-contained cases without changing historical benchmark prompts or labels.

After context analysis, a current proposal and acceptance of that exact proposal, run:

```text
npm run interview:practice -- --workspace <absolute-run>/work --approval-id <actual-current-id> --output <new-absolute-output>
```

This uses the existing Codex CLI and selected settings, not an extra generation provider. The actor receives original sources, analyzed role/round/seniority and the accepted plan, with no authorized tools. The host validates exact approval, source freshness, coverage, evidence references and time allocation before saving materials. Missing approval blocks the model call. Synthetic fixtures use `synthetic_test_script`, never human provenance.

Each exercise requires a scenario, concrete task, supplied artifacts, constraints, at least two follow-ups, answer reasoning, self-checks and at least three anchored scoring criteria. Timeboxes sum to the approved section budget. DS cases supply the product decision and data with units, denominators, assignment and observation windows where relevant. Coding cases require a precise contract, examples with expected outputs, limits and edge behavior. Design respects seniority. Behavioral and motivation exercises use documented facts and honest placeholders for missing personal details. Invented settings and data are explicitly hypothetical, never verified employer questions or candidate achievements.

Plan remains an outline. The user's latest refinement asks the actual question directly: a short title, the question, essential inputs/examples and Follow-ups. Scenario narration, candidate evidence and repetitive disclaimers are omitted from the question. Show answer reveals Method and Sample answer; useful clarifying questions and What a strong answer covers sit inside Method. Code solutions, complexity and expandable tests sit in Sample answer. Paragraphs/bullets are the default, with escaped semantic formatting for code, examples and tables. The formatter never accepts raw HTML.

The additive simulation-v2 fields retain compatibility with stored packs: `question_title`, `question_details`, `clarifying_questions`, `answer_coverage`, `sample_answer`, `solution`, `plan_section_id`, and top-level `question_bank`. The current `interview:practice` CLI uses protocol `context-direct-practice-node-v2`; historical context/material entrypoints retain their previous protocol. Its generation schema requires non-null titles, problem-detail arrays (possibly empty) and sample answers, with exactly one main exercise per section; alternatives belong in the top-level bank. Direct generation requires at least six main/alternative questions and targets about eight. Every coding question requires a complete dependency-free Python solution with at least three JSON example/boundary tests. Before publication the host checks syntax, restricts supported constructs and runs declared tests with a three-second subprocess limit. This is a bounded teaching-code checker, not a general security sandbox or proof of correctness. Other languages are not implemented by this checker.

Main section IDs and total rehearsal minutes still match the exact approved plan. Bank questions are a replacement menu linked to an existing section with a duration no greater than that section; they are not added homework or a changed round. Bank references receive the same source checks as main questions. Recruiter banks stay within general conversation and avoid coding when excluded by the invitation. Unknown personal details remain placeholders. Rubrics and reference notes remain stored for evaluation. Changed inputs can still invalidate materials. A coding implementation that passes its own generated examples may fail independent checks; inspect and cross-test it before delivery.

Schema checks establish completeness, not correctness, realism or learning benefit. Inspect arithmetic, input/output consistency, feasible scope, seniority and follow-ups before delivery. Independent evaluation should score these dimensions using frozen cases and the existing blinded review workflow. Old short-prompt results do not establish v2 quality. A comparative study must declare the new format, retain first failures and use equivalent context/budgets. Do not replace historical outputs.

Earlier observations remain in [v2 verification](interview-workbench-v2-verification.md) and [compact-format verification](interview-practice-compact-verification.md). Current direct-question, bank and executable-answer observations are in [direct-practice verification](interview-practice-direct-verification.md). Failed attempts and prior material rows are preserved. These development checks are not held-out benchmarks or independent quality ratings.

## JSON input contract repair — 2026-11-05

A website-generated coding exercise required tuple-only pairs while its JSON test arguments decoded to nested lists. The unchanged execution checks correctly rejected it. Direct-practice generation now explicitly requires JSON-native input contracts and consistent displayed signatures, validation and test expectations; internal tuples remain allowed. A regression exercises both valid nested-list input and rejection of a tuple-only answer. The original failed output is retained, and retries use the existing explicit website control and current saved plan approval. No result is repaired or accepted by bypassing its tests.
